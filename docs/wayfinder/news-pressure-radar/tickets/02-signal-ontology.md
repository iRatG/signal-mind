# Ticket 02 - Signal Ontology

Status: closed
Type: grilling
Labels: `wayfinder:grilling`
Claim: claimed by Claude (wayfinder session, 2026-07-31)
Blocks: Ticket 04 - Report Prototype, Ticket 06 - Evaluation Harness, Ticket 08 - OpenSpec Bridge

## Question

What exactly counts as a "news pressure signal" in this project?

## Why This Matters

Without a shared ontology, every score, section, and quality rule becomes arbitrary. The code already has clusters, pressure score components, anomaly scores, and report sections; this ticket turns those into a product language.

## Decision Shape

Define the canonical signal types and their evidence:

- Main pressure: high volume plus broad source spread.
- Rising impulse: unusually recent acceleration versus baseline.
- Persistent background: a theme that stays active for many days.
- Synchronized story: several sources converge on the same story.
- One-source anomaly: narrow source concentration that may be early signal or noise.
- Noise/routine: recurring rubrics, calendar fillers, market table churn, and unsupported LLM claims.

For each type, decide:

- required evidence;
- typical false positives;
- what the report should say;
- whether it can trigger delivery.

## Starting Assumption

The system should prioritize interpretable evidence over model cleverness: every signal needs visible source count, representative headlines, period, and reason for ranking.

## Working Decision

Cross-source repetition is a core signal of news pressure. If several independent sources talk more often about the same theme, the system may treat the theme as statistically meaningful agenda pressure. This alone does not prove market influence; it only qualifies the news side of the relationship. Market influence or market trace requires a separate abnormal/relative market movement check in the event window.

Resolved 2026-07-31 (`/grilling` + `/domain-modeling` session), grounded in what the current code (`analytics/news_pressure_cluster.py`) actually computes rather than invented from scratch. Four cross-cutting principles apply to all six signal types below, decided while working through them one at a time:

1. **Versioned parameter registry, not hardcoded thresholds.** Every numeric threshold introduced below (velocity quartile, `persistence>=14d`, `source_spread>=3/4`, etc.) lives in a classification hierarchy — one level groups a cluster of related metrics, another level holds the individual versioned parameters (value, description, change history) underneath. Recalibrating these from accumulated logs is a separate future ML/data-science module, explicitly out of scope for this ticket — this ticket only guarantees the parameters and their history are recorded so recalibration is possible later. (Forward-noted on Ticket 11; future scenario/stress-test use forward-noted on Ticket 06.)
2. **No empty modules.** Where we can't fully resolve a question today, we still commit to a concrete, simple, best-practice-grounded starting value — never a stub — explicitly flagged as provisional and revisitable via the parameter registry (Ticket 11) and, if it proves to be a weak link in practice, a candidate for deeper testing in Ticket 06 (Evaluation Harness).
3. **State transitions, not permanent labels.** A cluster's signal type can change as more evidence arrives: Rising impulse that holds for 3 months (per the 1/2/3-month baseline check) reclassifies to Persistent background; an unconfirmed One-source anomaly reclassifies to Noise/routine if its follow-up window closes with no corroboration; a nominally-routine cluster gets rescued back out of Noise/routine if it coincides with an abnormal market move.
4. **News-plane × market-plane cross-check, reused everywhere.** The single recurring false-positive filter across Main pressure, Synchronized story, One-source anomaly, and Noise/routine-rescue is the same one Ticket 10 already defined: a news-side pattern alone is not evidence of market relevance; it only becomes one when it coincides with an abnormal/relative market trace in the event window. This is deliberately reused, not reinvented, per type.

### Per-type decisions

- **Main pressure** — Evidence: cross-source repetition (unchanged, decided earlier). False positives: high `pressure_score` from the news side alone with no market-side corroboration (principle 4). Report language: retrospective/historical-strength framing only ("this news-pressure pattern has historically coincided with elevated volatility in X"), never a directional forecast — this is what keeps the product inside Ticket 01's out-of-scope line against trading signals. Delivery trigger: can trigger an out-of-cadence send, but only when market-confirmed (forward-noted on Ticket 07).

- **Rising impulse** — Evidence: `velocity_score` in the top quartile of the trailing velocity distribution (parameter-registry value), not simply `>0`. False positives: (a) small-denominator artifacts inflating the ratio, mitigated by requiring minimum absolute volume; (b) judged against 1/2/3-month trailing aggregates — a spike holding only 1 month is suspect, 2 months more credible, 3 months means it has become the baseline and should reclassify to Persistent background (principle 3); (c) seasonality (recurring calendar-linked topics) is a known risk, deferred to Ticket 06 for year-over-year validation. Report language: purely retrospective description of news tempo, no market claim, no conflict with Ticket 01. Delivery trigger: never triggers independent delivery; at most an in-report highlight for an especially sharp/"sensational" case, nothing more.

- **Persistent background** — Evidence: `persistence>=14 days` (parameter-registry value, from the existing code default). False positives: eternal routine rubrics (daily currency-rate blurbs) that never change their surrounding phrasing are background noise, not signal — tested via collocation/word-combination stability around the theme, not just its persistence; if the surrounding language shifts over time, it's a genuine evolving story worth surfacing, not routine (the exact mechanism — n-gram/collocation drift — is an implementation detail for a later stage, not decided here). Report language: this section is deliberately absent from the daily report (already-established behavior, not a gap) — daily is about "what happened/accelerated" per Ticket 01, persistent background surfaces on the weekly layer. Delivery trigger: no, not an urgent topic.

- **Synchronized story** — Evidence: `source_spread>=3` (daily/weekly) / `>=4` (monthly/history), parameter-registry values. False positives: several sources independently describing the same theme in their own words is real convergence; several sources republishing the same press release/text verbatim is copy-paste, not independent corroboration, and needs a lexical-diversity check across sources rather than counting `source_spread` alone. Report language: describes coverage breadth, no market claim, no conflict with Ticket 01. Delivery trigger: same principle as Main pressure — only with market confirmation.

- **One-source anomaly** — The code currently conflates this with Noise/routine into one `anomaly_score`/"Аномалии И Шум" section; the ontology requires them separated. Evidence: `source_spread==1` starts as "watch," then reclassifies after a follow-up window — corroborated by ≥2 more sources later, or coincides with an abnormal market move (principle 4) → genuine one-source anomaly; neither → Noise/routine (principle 3). False positives / modifier: raw source count is not the only factor — source category (state-aligned, independent/opposition, foreign-by-country — categories to be defined by Ticket 05) is an additional modifier on top of the follow-up/market check, not a replacement for it: a story reported only by an independent/opposition outlet while state-aligned outlets stay silent may reflect selective non-coverage rather than the story being unreal, and the reverse asymmetry is equally informative (forward-noted on Ticket 05, alongside its existing source-categorization research scope). Report language: neutral, "unconfirmed, worth watching" framing; the coverage asymmetry itself (only independent media reported X) can be stated as a retrospective fact, which doesn't conflict with Ticket 01. Delivery trigger: only with market confirmation, same as Main pressure.

- **Noise/routine** — The weakest in current code (only `ROUTINE_TOKENS` for weather/horoscopes plus a one-source-volume heuristic; no rubric/calendar-filler/market-table-churn detection). Evidence, made concrete per principle 2 rather than left vague: extend `ROUTINE_TOKENS` with three named categories — (1) weather/horoscope (existing), (2) **financial boilerplate** (template phrases like currency-rate blurbs, market-open/close notices, when they form their own routine block rather than part of a substantive cluster), (3) **calendar fillers** (TV schedules, church calendar, sports schedules) — combined with the same collocation-stability check already decided for Persistent background. Unsupported numeric/factual LLM claims (`unsupported_number`, already implemented in code) are explicitly folded into this type rather than left as an unlabeled side mechanism. Also the landing bucket for anything that fails another type's check: unconfirmed One-source anomaly, seasonal/small-denominator Rising impulse, copy-paste Synchronized story. False positives (the inverse — noise wrongly suppressing something real): rescued back out via the same market cross-check (principle 4) — a nominally routine topic (e.g. weather) that coincides with an abnormal market move gets promoted, not suppressed. Report language: no narrative section — a quiet audit tag/count ("N routine/unconfirmed clusters excluded"), consistent with the Starting Assumption's preference for interpretable evidence over prose. Delivery trigger: never triggers delivery, and should actively not dominate a report — a period that's mostly noise is itself a quality flag (reusing the existing `quality_flags`/`thin_cluster` mechanism), a question for Ticket 03.

## Grilling Transcript

Full record of the `/grilling` + `/domain-modeling` interview behind the Working Decision above, kept per the convention established on Ticket 01 (`docs/agents/issue-tracker.md`) — the real exchange, not only the synthesis. A read-only research agent grounded every recommendation in the actual code (`analytics/news_pressure_cluster.py`, `analytics/news_pressure_snapshot.py`) before each question was asked, so recommendations reflect what the pipeline already computes, not invented behavior. Per Airat's own instruction (captured here, on Synchronized story below), his dictation is cleaned up for grammar/coherence where it was fragmented — substance and his own terms are kept intact.

**Main pressure (finishing the 3 questions left open from before this ticket's session):**
Claude presented the existing `pressure_score_v2` formula and asked about false positives, report language, and delivery trigger, recommending: false positives = news-only score without market corroboration; report language = historical strength, not forecast; delivery trigger = only with market confirmation.
Airat pushed back constructively on the framing rather than just approving: he asked to keep this "not one flat check comparing news to itself" — insisted the false-positive check must compare two values from genuinely different planes (news words/tone vs. a mathematical/market basis), and pointed out this is exactly what makes a real event vs. a false one. He also initially leaned toward directional report language ("index will likely react strongly") before Claude flagged the conflict with Ticket 01's already-closed retrospective-only rule; Airat chose **"только историческая сила (согласуется с Ticket 01)"** over allowing directional language. On delivery trigger, he described a concrete scenario — a quiet-news weekend where the market still moves oddly — as exactly the kind of case that should escalate, which Claude identified as already covered by Ticket 10's "market-first backtrace" concept, so no new mechanism was needed, only a forward note to Ticket 07.

**Rising impulse:**
Claude recommended a top-quartile velocity threshold instead of the code's current `>0`, plus a minimum-absolute-volume guard against small-denominator false positives.
Airat agreed on the quartile threshold but insisted it be a named, versioned reference value in a lookup/registry ("справочник") with value, description, parameter name, and change history — not a hardcoded number — because he wants to be able to review and adjust it later based on accumulated data. For false positives he proposed the 1/2/3-month aggregate scheme himself: a spike holding only 1 month is suspicious, 2 months more standard, 3 months means it's become the historical baseline — and he explicitly named seasonality (winter snow coverage every year) as a concrete risk this scheme needs to handle. He confirmed report language as-is and accepted the no-independent-trigger recommendation, adding that an especially sharp/"sensational" case could still get a light in-report highlight, "но не более" (but no more than that).

**Persistent background:**
Claude asked about the `persistence>=14d` threshold, routine-rubric false positives, why the daily report omits this section, and delivery trigger — opening with the boundary question of when Rising impulse should reclassify into this type.
Airat confirmed `>=14d` as a starting reference value, again insisting it live in the same versioned parameter registry, and explicitly separated *using* the registry now from *building an automatic recalibration engine* — he called the latter a distinct future module ("какой-то уже машин лёнинг или дата сайенс" review of what worked or didn't), not something to build in this ticket; right now the job is only to make sure everything is logged so recalibration is possible later. On false positives, his own proposal: an eternally-recurring rubric (daily currency rate) that says the same thing in the same words every time is uninteresting background noise and can be excluded from consideration entirely; but if the word combinations/context around it start changing over time, that shift is itself a signal worth a dedicated check (he described this as needing some ML/NLP module for measuring how "standard" a phrase pattern is). On report language, he explicitly delegated the decision to Claude ("давай подумай... как ты сам рекомендуешь"), and accepted the recommendation that daily omitting this section is intentional, consistent with Ticket 01. He confirmed no delivery trigger.

**Synchronized story:**
Claude asked about the `source_spread>=3/4` threshold and, as the one genuinely new question, how to tell independent corroboration apart from copy-paste republishing of the same text.
Airat agreed the copy-paste distinction mattered, then generalized the parameter-registry idea further: it isn't a flat table but a classification hierarchy — one level groups a cluster of related metrics with several values, another level holds the individual versioned parameters underneath, still not hardcoded. He named a concrete future use for this registry: scenario/stress-test analysis, replaying historical data through different threshold sets and observing how indices actually reacted. He also described the news-ingestion layer as a future pluggable module — currently a handful of Russian site parsers, but it should be swappable for RSS feeds, Telegram channels, or third-party datasets (he mentioned we may already have a ~6-year US news-background dataset somewhere, offering to locate it precisely later). He confirmed report language and delivery trigger as proposed ("тут вроде всё хорошо"). He closed with a methodological note about how he sees this collaboration: he isn't a mathematician, journalist, or news researcher — his role is to be interviewed and supply the idea, Claude's is to turn it into a rigorous, defensible framework (hypothesis → metrics → concrete result, not a prose retelling); he explicitly authorized cleaning up his (often run-on, dictated) phrasing when writing it down, as long as the substance and his own terms survive.

**One-source anomaly:**
Claude flagged a real conflict directly (domain-modeling discipline): the code currently merges this type with Noise/routine into one `anomaly_score`/section, but the ontology needs them separated, and proposed a follow-up-window + market-corroboration split.
Airat didn't object to that split, but added a real modifier: source **category** matters, not just source count — state-aligned outlets (RBC, Kommersant, Vedomosti), independent/opposition outlets (e.g. Radio Svoboda), and foreign outlets (tagged by country) will structurally cover different things; a story appearing only in independent/opposition media while state-aligned media stay silent may reflect selective non-coverage of a real event (accident, emergency) rather than the story being unreal, and the reverse asymmetry is equally informative. Claude matched this to Ticket 05's already-existing research scope on source categorization and proposed folding it in as a modifier, not a replacement, for the follow-up/market check — Airat confirmed this synthesis plus the three remaining sub-questions in one pass: **"Да, всё верно — закрываем."**

**Noise/routine:**
Claude proposed treating this largely as the bucket other types demote into when their checks fail, plus the market-rescue principle for false positives, and a quiet audit-tag report style.

## Revision (2026-08-01, from Ticket 12 - Historical Cluster Calibration Study)

Empirical check against ~4.5 years of historical headlines: **`persistence>=14d` sits at roughly the p95 boundary of real cluster lifespans** (median is 3 days, p75 is 5 days) — it marks the top ~5% of stories, not a mid-range cutoff. If "Persistent background" was meant to catch a broader band than the rarest 5%, this threshold may need lowering; if the rarest-5% framing was intentional, it's already well-calibrated. `source_spread>=3/4` for "Synchronized story" could not be validated from the English pass (56% of that corpus has no recoverable per-outlet identity — an archive property, not fixable) and needs a Russian-pipeline-based recalibration instead, still provisional. Full detail: [Ticket 12's findings report](../calibration/findings-report.md).
Airat's response set a general rule for the whole ticket, not just this type: where something can't be fully answered today, never leave it as an empty placeholder — ground it in reasonable, industry-normal practice, commit to a concrete simple starting logic, keep it non-contradictory with everything decided so far, and explicitly flag it as revisitable if it later proves to be a weak link in the pipeline (at which point it earns deeper, dedicated testing). Applying that immediately, Claude committed to three concrete `ROUTINE_TOKENS` categories (weather/horoscope, financial boilerplate, calendar fillers) instead of leaving "extend the routine detector" vague, and Airat accepted this as satisfying his rule: **"логику обязательно нужно заложить, чтобы это не пустой модуль был — договорились."**
