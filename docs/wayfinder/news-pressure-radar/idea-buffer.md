## 2026-07-31 — No hardcoded entities, registry-driven system

Captured while grilling [Ticket 10 - Market Coupling Model](tickets/10-market-coupling-model.md), but the principle is project-wide, not specific to market instruments.

Airat's framing: the system should be "беспощадна, холодна, рациональна" (unsparing, cold, rational) — no entity identifiers (instrument tickers like `IMOEX`/`RTSI`/`USD`, and by extension likely source names, signal-type labels, etc.) should ever appear as literals inside code logic. Every such entity is a row in a reference/config table, referenced only by id. Code iterates over registry rows filtered by an `active`-style flag, never branches on a hardcoded name.

This generalizes [Ticket 02](tickets/02-signal-ontology.md)'s existing cross-cutting principle ("a versioned, hierarchical parameter registry for every tunable threshold, not hardcoded") from *thresholds* to *entities themselves*. Concrete instance decided in Ticket 10: the market-instrument universe (MOEX indices, FX pairs) is a reference table sourced from the MOEX ISS API, with a pilot-subset flag (e.g. `active_in_pilot_v0`), not a list embedded in code — scaling to more instruments later is a data edit, not a code change.

Open for later: does this same registry pattern extend to news sources (Ticket 05's 14-source list), signal types (Ticket 02's 6 types), or quality-gate flag names (Ticket 03)? Not decided — worth revisiting once any of those tickets reach implementation, to check whether their current documentation-as-list approach should also become a registry table.

## 2026-07-31 — Stable interfaces between modules, free-changing internals; role independence

Captured while grilling [Ticket 10 - Market Coupling Model](tickets/10-market-coupling-model.md), specifically while discussing whether the coupling-cycle's Auditor should be a separate agent from the Runner. Airat's principle is project-wide, not specific to that one role question — recorded as a forward-note on [Ticket 11 - Agentic Delivery Process](tickets/11-agentic-delivery-process.md) since that ticket owns "which parts of the work are separate agents vs one agent with review phases," but the underlying architecture rule applies to code modules generally, not only agent roles.

Airat's framing (paraphrased): a coder and a tester must never be the same role/context, or the check "covers for itself" — role independence is non-negotiable wherever one thing is supposed to verify another. Generalized: **the project is built from modules; you change or tune the logic *inside* a module freely, but you do not rewrite how modules *interact*.** The interaction contract (interface) is the stable thing; internals are the changeable thing. This is the same "deep module" idea the `codebase-design` skill already exists to help apply (interface stability, hidden/swappable internals) — worth using that skill deliberately once any module boundary (agent roles, or a code module) is actually being drawn, rather than improvising ad hoc separation each time.

Open for later: which specific module boundaries in this project (beyond Runner/Auditor/Synthesizer) should get this same "fix the interface, free the internals" treatment? Candidates that will come up naturally: the news-pressure clustering step vs. the quality-gate step (Ticket 03), the report-rendering step vs. the signal-detection step (Ticket 04). Not decided — surface again when those modules are actually being built.

## 2026-07-31 — Fix per the documented concept, never an ad-hoc patch

Captured while grilling [Ticket 04 - Report Prototype](tickets/04-report-prototype.md), while discussing the diagnostic/support-agent role already forward-noted on [Ticket 11](tickets/11-agentic-delivery-process.md). Airat's framing: whatever breaks — a data-collection module, a scoring step, anything — gets repaired according to the project's actual specification/concept for that piece, never with a quick patch just to silence the failure. This applies at every layer he described in the same session (ops/technical logs, metrics/decision layer, product layer), not just to code the diagnostic agent touches.

This is the same discipline already implicit in the project's other standing principles — registry-driven entities instead of hardcoded literals, "no empty modules" (Ticket 02), stable module interfaces (see the entry above) — generalized explicitly to bug-fixing/incident-response behavior for the first time. Open for later: what "the documented concept" means operationally when a fix is needed fast (e.g. does the spec get consulted/updated before the fix, or does an emergency fix get retroactively reconciled with the spec afterward?) — not decided, resolve if/when Ticket 11's diagnostic-agent role is actually built.

## 2026-07-31 — Four-state module handoff protocol

Captured while grilling [Ticket 06 - Evaluation Harness](tickets/06-evaluation-harness.md), while designing the Generator → Evaluator → Airat-audit chain for the qualitative rubric track. Airat generalized the existing "stable interfaces between modules" principle (see the entry above) into a concrete, literal protocol: every unit of work crossing a module boundary must pass through four explicit, loggable states — his own words: "я взял в работу от того-то (или это я взял). я работаю. я закончил. я отдал это... каждый блок делает свою работу, не прикрывает другого." Formalized as `taken → in_progress → done → handed_off`, each transition carrying a timestamp, an explicit "from/to" reference, and a pointer to the actual work item/output — so at any moment it's unambiguous which module currently owns a piece of work, and nothing is silently passed through.

Applied concretely in Ticket 06 to the Generator → Evaluator → Audit chain. Not yet applied to Ticket 10's Runner → Auditor → Synthesizer chain, but that's the obvious next candidate — surface again when Ticket 11 (Agentic Delivery Process) is claimed, since Ticket 11 owns the overall module/role interaction design.

## 2026-07-31 — Bounded-choice interaction principle for human-in-the-loop escalation

Captured in the same Ticket 06 session, while deciding how often and in what form the automated Evaluator's output should reach Airat for audit. Airat was explicit that he does not want to become a bottleneck or take on review as "a second job": "меня не часто наверное привлекать... лучше если ты мне поможешь делать выбора. допустим 3 варианта... а так 3 варианта для меня я выбрал и идём дальше... чтобы система не думала что я узкое горлышко." His reasoning: the system accumulates enough documented context and reasoning (exactly what these long grilling sessions produce) that it can narrow any decision down to a small, well-reasoned set of options before ever reaching him, rather than asking an open-ended question.

**Standing principle:** any point where the system escalates to Airat — audit sampling, quality-gate ambiguity, the diagnostic-agent role forward-noted on Ticket 11 — should default to presenting **at most 3 concrete options with reasoning**, plus an implicit 4th "your own answer/comment" slot, never an open-ended question. Combined with infrequent touchpoints (e.g. Ticket 06's weekly audit sample, not per-run). Directly relevant to Ticket 11's diagnostic-agent design and Ticket 03's escalation-never-silent rule — both should adopt this same interaction shape when they reach implementation.

## 2026-07-31 — Repository boundaries and data-source coupling are independent axes

Captured while grilling [Ticket 09 - Repository Boundary](tickets/09-repository-boundary.md). Claude's initial framing conflated "when can we split the git repository" with "when is the one-time historical data extraction (Ticket 12) done" — reasoning that splitting before the extraction would require cross-repo access to `hf_news.db`. Airat corrected this: a one-time, read-only DB-file read by path doesn't require git-monorepo colocation; a script in a brand-new repository can open a source DB by path exactly as a script in the current checkout can. Verified before accepting, not assumed: grep confirmed MADPAC's actual code (`analytics/news_pressure_cluster.py`, `scripts/news_pressure_regimen.py`) already has zero references to `signal-mind` internals (`signal_mind.duckdb`, `experiments.db`, `src/agent/*`) — the only files touching those belong to an unrelated legacy reporting line.

**Standing principle:** a *live* dependency (code that continuously reads/writes another system's internals) is a real reason to keep two things in one repository; a *one-time* historical read (a migration, a backfill, a snapshot extraction) is not — it's an operational detail (a configurable source path) that can happen from either side of a repo boundary. Don't let a one-off data-migration step gate a structural decision it doesn't actually depend on. Worth re-checking whenever a future repo-boundary or module-extraction question comes up (this generalizes past MADPAC specifically).

## 2026-07-31 — wayfinder/grilling/openspec is the unchanged core; every other skill is a satellite

Captured while grilling [Ticket 11 - Agentic Delivery Process](tickets/11-agentic-delivery-process.md), when Airat raised an explicit concern mid-session that mapping many different Claude Code skills onto the meta-development process might dilute the three skills that actually built the whole project so far: **"наши основные скиллы должны остаться wayfinder grill openspec мы на них почти весь проект до сегодня написали."**

**Standing principle:** `wayfinder` (the decision map) → `grilling`/`grill-me` (resolving each ticket) → `openspec` (compiling closed decisions into a durable, checkable spec) is not one option among several process choices — it is the fixed axis of the whole project, and it does not get diversified, replaced, or diluted by any other skill. Every other skill (`implement`, `tdd`, `code-review`, `simplify`, `security-review`, `diagnosing-bugs`, `handoff`, etc.) is a **satellite that only activates once `openspec` has produced a real `tasks.md`** — during the planning/decision phase (where this project still is as of 2026-07-31), none of them are invoked. Worth re-checking whenever a future ticket is tempted to route decision-making itself through a different skill instead of `wayfinder`/`grilling`.

## 2026-07-31 — Temporal model split: expensive model builds and extends, cheap model operates and watches

Captured in the same Ticket 11 session, resolving the cost/model-split forward note from Ticket 03. An initial framing (tag individual LLM call-sites as `pure_code` vs. `interpretive`, route each to a different model) was proposed by Claude and explicitly redirected by Airat toward a simpler split: **"пока мы пишем в Клод Код — дорого, но ладно... уже потом, после, когда уже что-то будет работать, можно как обслуживающую модель подсоединить DeepSeek."**

**Standing principle:** the expensive, high-capability model (Claude Code) is reserved for **building and extending** the system — always, regardless of cost, because decision quality and code quality both matter more than API cost during construction. The cheap model (DeepSeek, in this project) only enters **once a working part of the system already exists**, taking over routine, frequent, checks-against-what-already-exists roles (in Ticket 11: the diagnostic/support agent restricted to diagnosis-only, and Ticket 06's Evaluator). Any further building, extending, or approving of a fix stays on the expensive model even after launch. Generalizes beyond MADPAC: when a future project asks "which model for which step," the first cut should be *build-time vs. operate-time*, not a per-call-site content classification — the latter is a real but secondary optimization to revisit only once real operational cost data exists.
