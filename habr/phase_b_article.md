# Мы дали LLM искать сигналы на бирже. Вот что пошло не так — и как мы это исправили

*Продолжение статьи «Как мы научили алгоритм слушать рынок»*

---

В первой статье мы запустили агента на 9 часов, получили 1943 итерации и нашли собственную системную ошибку: агент коррелировал российский индекс с российским индексом и называл это «сигналом из китайских акций». Мы это нашли, задокументировали и продолжили.

Эта статья — о том что было дальше. О том как мы думали про LLM, как поняли что думали неправильно, и как в итоге выстроили систему которая **не врёт ни нам, ни себе**. И о том почему 2 настоящих сигнала лучше чем 200 красивых.

---

## Проблема которую мы долго не видели

После первого марафона у нас было 6 «подтверждённых» сигналов и ощущение что всё работает. Но при каждом внимательном взгляде возникал один вопрос.

**Кто оценивает результат?**

В Phase A схема выглядела так:

```
LLM придумывает гипотезу
    ↓
SQL проверяет данные
    ↓
LLM оценивает результат SQL
    ↓
LLM решает: сигнал или нет
```

Видите проблему? LLM генерирует гипотезу — и LLM же решает подтверждена ли она. Это как спрашивать студента: «хорошо ли ты написал экзамен?» Конечно хорошо.

LLM хочет быть полезным. Это его базовая настройка. Когда результат SQL показывает корреляцию 0.3 при ожидаемой 0.5 — LLM скорее всего напишет «частично подтверждено» вместо «не подтверждено». Не потому что врёт. Потому что так устроен.

Мы это поняли только когда написали независимый верификатор и прошли по «подтверждённым» сигналам заново.

## Правило №1: LLM генерирует, статистика решает

Первое и главное что мы изменили в архитектуре Phase B:

```
                    БЫЛО                          СТАЛО
        ┌─────────────────────┐        ┌─────────────────────┐
        │  LLM: гипотеза      │        │  RAG + LLM: гипотеза│
        │  SQL: данные        │        │  Данные: z-score     │
        │  LLM: оценка ✓/✗   │        │  M5: структура   ✓/✗│
        └─────────────────────┘        │  M6: предикция   ✓/✗│
                                       └─────────────────────┘
          LLM — судья                    LLM — только идеи
                                         Статистика — судья
```

LLM хорош в одном: читать документы и придумывать идеи. В этом ему равных нет.
LLM плох в другом: быть объективным судьёй чужих и особенно своих идей.

Как только мы разделили эти роли — качество сигналов изменилось кардинально.

**M5 (Mann-Whitney U test)** — структурный критерий. Делим торговые дни на «высокий новостной поток» и «низкий». Если распределение доходностей статистически отличается — есть структура. p < 0.05. Никакого мнения LLM.

**M6 (LightGBM IC)** — предиктивный критерий. Обучаем градиентный бустинг предсказывать доходность по новостному потоку. Information Coefficient > 0.05 — модель предсказывает лучше случайного. Тоже без LLM.

Сигнал проходит только если оба критерия говорят «да». AND, не OR.

## Правило №2: данные нужно нормализовать, и это не очевидно

Второе открытие, которое изменило всё.

Новостной поток нестационарен. В 2022 слово «санкции» встречалось в 15-20 статьях в день. В 2024 — в 3-5. Если вы ищете корреляцию между частотой слова «санкции» и ценой актива — вы найдёте режимный артефакт, а не сигнал.

Решение: скользящий z-score с окном 90 дней.

```python
def rolling_zscore(series, window=90):
    mu  = series.rolling(window, min_periods=20).mean()
    sig = series.rolling(window, min_periods=20).std().clip(lower=1e-6)
    return ((series - mu) / sig).clip(-5.0, 5.0)
```

Это превращает вопрос «сколько раз упомянули инфляцию?» в «насколько необычно часто упоминают инфляцию сегодня по сравнению с последними 90 днями?».

Без этой нормализации — SP500/inflation/lag=1d даёт IC = 0.02. С ней — IC = 0.185.
Один приём, десятикратный прирост сигнала.

## Правило №3: три непересекающихся множества и ни шагу назад

```
┌────────────────┬──────────┬────────────────┬──────────┬──────────────────┐
│  Train         │  буфер   │  Val           │  буфер   │  Test            │
│  2022-2023     │  3 мес   │  2024-2025     │  4 мес   │  2025-2026       │
│  ищем здесь   │          │  проверяем     │          │  финал, 1 раз    │
└────────────────┴──────────┴────────────────┴──────────┴──────────────────┘
```

Правила:
- На Train — ищем. Всё что хотим.
- На Val — проверяем найденное. Без поиска.
- На Test — одноразовая финальная проверка. Использовали — сожгли.

Если бы мы следовали этому правилу в Phase A — половина «сигналов» отвалилась бы на Val и никогда не дошла до Test.

Буферы между периодами — защита от утечки информации. Рынок имеет инерцию, паттерны перетекают через границы. 3 месяца буфера убирают этот эффект.

## Правило №4: система должна честно говорить когда ошибается

Это самое сложное — и самое важное.

Мы добавили **Scientific Ledger**: после каждой ночной сессии система рассчитывает собственную достоверность.

```
Протестировано гипотез:     672
Ожидается случайных (p<0.05): 33.6
Найдено в train:            12
Обогащение vs случай:       0.36x

[WARN] ENRICHMENT_NEAR_CHANCE: результаты едва отличаются от случайных
[INFO] P_HACKING_RISK: при 672 гипотезах ожидается 34 ложноположительных
```

Когда система видит что обогащение < 1 — она сама выдаёт предупреждение.
Когда val pass rate > 60% — она флагует возможную утечку данных.
Когда IC > 0.40 — она флагует look-ahead bias.

```
Флаги которые система отслеживает:
┌──────────────────────────┬──────────────────────────────────────────┐
│ ENRICHMENT_NEAR_CHANCE   │ нашли почти столько же сколько случайно  │
│ VAL_RATE_IMPOSSIBLE      │ > 60% val pass — что-то не так           │
│ SIGN_FLIP                │ > 40% сигналов меняют знак на val        │
│ IC_INFLATED              │ IC > 0.40 — нереально для финрынков      │
│ REPEATED_FAILURE         │ 3+ раза в train, 0 в val — хронический   │
│ PERSISTENT_FLAG          │ одна и та же проблема 3+ сессии подряд  │
└──────────────────────────┴──────────────────────────────────────────┘
```

Это неудобно. Иногда система говорит «всё что ты нашёл сегодня ночью — шум». Но это лучше чем система которая всегда говорит «отличная работа».

## Правило №5: система должна помнить что она делала

Самая дорогая ошибка в работе с LLM-системами — потеря контекста. Агент не помнит что проверял три дня назад. Он готов снова потратить 7 часов на гипотезу которая уже 5 раз не прошла val.

Мы решили это через три уровня памяти:

```
┌─────────────────────────────────────────────────────────────────┐
│                    ТРЁХУРОВНЕВАЯ ПАМЯТЬ                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [1] session_config.json — оперативная память (обновляется      │
│      каждый день)                                               │
│      · топ-инструменты по IC                                    │
│      · анти-паттерны (никогда не проходят val)                  │
│      · лучшие лаги, лучший feature type                         │
│      · IC gate для следующей сессии                             │
│                                                                 │
│  [2] ledger.jsonl — долгосрочная память (append-only, никогда   │
│      не удаляется)                                              │
│      · каждая сессия с результатами и integrity flags           │
│      · каждое изменение конфига с причиной                      │
│      · история enrichment по сессиям                            │
│                                                                 │
│  [3] Obsidian vault (ChromaDB: methodology) — институциональная │
│      память (221 чанк)                                          │
│      · сигналы которые исследовали (67 чанков)                  │
│      · известные атаки/уязвимости (43 чанка)                    │
│      · рабочие подходы (41 чанк)                                │
│      · что устарело и почему (deprecated)                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

Obsidian vault — это особенно интересно. Мы вели базу знаний в Obsidian: каждый исследованный сигнал, каждая методологическая атака, каждое решение. Потом проиндексировали это в ChromaDB. Теперь перед генерацией каждой гипотезы агент спрашивает vault: «мы уже это проверяли? какие атаки известны? что устарело?»

Это предотвращает самую раздражающую вещь в работе с LLM: когда система раз за разом предлагает одно и то же.

## Ouroboros между сессиями: как система учится через дни

Внутри одной ночной сессии Ouroboros работал с первого дня: каждый раунд умнее предыдущего. Мы вынесли это на уровень выше.

```
22:00  Ночная сессия (7 часов)
       · загружает session_config.json
       · стартует уже зная что работает
       · тестирует новые гипотезы
       · пишет результаты
          ↓
06:00  Дневная сессия (7 часов)
          ↓
13:00  inter_session_analyzer (10 минут)
       · читает ВСЕ результаты за всё время
       · пересчитывает топ-инструменты, анти-паттерны
       · адаптирует IC gate:
           val_rate > 40% → ужесточает (IC gate 0.08)
           val_rate < 5%  → ослабляет (IC gate 0.01)
       · обновляет session_config.json
          ↓
14:00  Дневная сессия с обновлённым конфигом
       · знает больше чем утром
          ↓
22:00  Ночная сессия
       · и так далее
```

14 часов поиска каждые сутки. Без участия человека.

Единственный момент где нужен человек — утренняя проверка. 30 секунд:

```powershell
.\scripts\morning_check.ps1
```

Показывает: сколько нашли, прошли ли val, какие integrity flags, enrichment. Если всё хорошо — ничего делать не надо. Если система флагует проблему — смотришь подробнее.

## Что пошло не так: три реальных бага

**Баг 1: бесконечный цикл Ouroboros**

Метки конфигов включали номер раунда:
```
r3_stable_MSCI_W_sancti
r4_stable_MSCI_W_sancti   ← та же гипотеза, другой номер
r5_stable_MSCI_W_sancti   ← и снова
...
r25_stable_MSCI_W_sancti  ← 25 раз один и тот же тест
```

Система считала их разными конфигами и гоняла одно и то же 25 раз подряд. Потеряли 6 из 7 часов ночной сессии.

Исправление: метки content-based, не round-based.
```
stable_MSCI_WORLD_sanctions_1  ← один раз, навсегда
```

**Баг 2: LLM сам оценивает свои результаты**

Описан выше. Это не технический баг — это архитектурная ошибка. LLM-судья для LLM-гипотез = конфликт интересов.

**Баг 3: мы забыли RAG**

Когда переходили от агента к статистическому пайплайну — RAG просто не перенесли. 15 574 чанков годовых отчётов Газпрома, Лукойла, Сбера, Яндекса лежали неиспользованными. Мы искали сигналы вслепую когда у нас было 15 тысяч страниц с готовыми гипотезами.

Это случается когда RAG — необязательный слой. Решение — сделать его обязательным входом:

```
Phase C: нет гипотезы из RAG → запуск не происходит
```

## Результат: 2 сигнала. Почему это нормально

После полного цикла Train → Val → Test два сигнала прошли все проверки:

| Сигнал | IC | M5 p-value | Интерпретация |
|---|---|---|---|
| SP500 / inflation_z / lag=1d | 0.185 | 0.039 | Аномальный новостной поток об инфляции → S&P500 +1 день |
| FTSE_CHINA_50 / rate_z / lag=1d | 0.069 | 0.041 | Аномальный поток о ставке ЦБ → Китай H-shares +1 день |

Два. Не 200, не 20 — два.

Из 54 кандидатов прошедших Train+Val:
- 57% изменили знак на Test
- Режим 2022-2023 ≠ режим 2025-2026
- Рынок адаптируется быстрее чем мы думали

**Почему это нормально:**

Точная цитата из документации Renaissance Technologies (единственная публичная):
> *«Мы ищем паттерны которые существуют на коротком масштабе и быстро исчезают. Их немного.»*

Количество сигналов не важно. Важно что они настоящие. Два проверенных сигнала с IC > 0.06 на реальном holdout — это производственный результат, не учебный.

Сравните с тем что было в Phase A: 6 «сигналов» без holdout, с self-evaluation LLM, без z-score нормализации. Красиво выглядело. Не значило ничего.

## Что мы поняли про работу с LLM в исследовательских системах

Три года назад мы бы сказали: «дайте LLM достаточно данных и он найдёт сигналы». Сейчас говорим иначе.

**LLM хорошо умеет:**
- Читать неструктурированные документы и извлекать смысл
- Генерировать гипотезы которые имеют экономический смысл
- Объяснять найденные паттерны человеческим языком
- Писать SQL по описанию задачи
- Чинить собственные ошибки (SQL repair loop)

**LLM плохо умеет:**
- Быть объективным судьёй
- Помнить что делал три дня назад (без внешней памяти)
- Оценивать статистическую значимость
- Различать настоящий сигнал и шум в числах
- Держать методологическую дисциплину под давлением

**Правильная архитектура:**

```
   Корпоративные    ЦБ        Obsidian
      отчёты      документы     vault
         │            │           │
         └────────────┴───────────┘
                      │
                   RAG поиск
                      │
                    LLM
              (только генерация)
                      │
             ┌────────┴────────┐
             │  Гипотезы JSON  │
             │  с источником   │
             └────────┬────────┘
                      │
              ← Человек может
                посмотреть
                и исправить
                      │
              ┌───────┴───────┐
              │  M5 + M6      │
              │  (статистика) │
              └───────┬───────┘
                      │
              Integrity check
                      │
              Подтверждён / нет
```

Человек стоит между генерацией и тестированием. Не потому что LLM плохой. Потому что некоторые знания о рынке есть только у человека — актуальный контекст, здравый смысл, понимание что изменилось.

## Phase C: от корреляций к гипотезам с источниками

Следующий шаг — не искать больше. Искать умнее.

У нас есть 15 574 чанков годовых отчётов крупнейших российских компаний:

| Компания | Чанков | Что там |
|---|---|---|
| Sberbank | 4 614 | "ставка +1% → NIM давление, прибыль -3%" |
| Lukoil | 3 770 | "Brent — основной драйвер выручки" |
| Gazprom | 3 670 | "экспортные ограничения → эффект 1-2 кв" |
| Yandex | 3 115 | "рекламный рынок коррелирует с ВВП lag=1q" |

Каждая из этих фраз — готовая гипотеза. С инструментом (MOEXFN, MOEXOG), с направлением (позитив/негатив), с временным горизонтом (лаг).

Phase C меняет вопрос с «найди корреляцию» на «проверь что компания сама говорила о себе».

```
[Газпром AR2023, стр.47]:
"Санкционные ограничения на экспорт СПГ приводят к снижению
выручки с задержкой 6-8 недель по мере разворота поставок"

    ↓ LLM извлекает структуру:
    {
      instrument: "MOEXOG",
      feature: "sanctions_z",
      lag_range: [42, 56],
      direction: "negative",
      source: "gazprom/AR2023/p.47"
    }

    ↓ M5+M6 тестируют на данных

    ↓ Результат:
    IC = 0.14, M5 p = 0.031
    "Подтверждено. Газпром был прав."
```

Или не подтверждено. Тогда вопрос: почему компания ошиблась в собственной оценке?

Это уже не просто поиск сигналов. Это **аудит корпоративных прогнозов** на рыночных данных.

## Итог: что изменилось в голове

| Раньше думали | Теперь думаем |
|---|---|
| LLM найдёт всё если дать ему данные | LLM генерирует идеи, статистика проверяет |
| Больше итераций = лучше результат | Правильная методология > количество итераций |
| 6 сигналов лучше чем 2 | 2 настоящих лучше чем 6 красивых |
| RAG — дополнительный слой | RAG — обязательный вход, без него нет гипотез |
| Система сама всё поймёт | Система честно говорит когда не понимает |
| LLM оценивает LLM | Только независимая статистика оценивает LLM |

Главное что мы поняли: **работа с LLM-системой — это проектирование сдержек и противовесов**. LLM мощный но предвзятый. Статистика строгая но слепая. Человек видит контекст но не успевает всё проверить. Правильная система использует каждого там где он силён.
